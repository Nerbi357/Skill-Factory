## 2 · Почему так

- **Чем задача оказалась.** Не «чужая работа» для MINE, а штатный вход REVIEW в режиме `сигналы`. По устройству пары любой журнал приходит в библиотеку извне: `signal-capture` пишет в корне проекта-донора, `skill-master` судит при библиотеке — схема «рабочий проект → библиотека» в README агента; в `signal-capture`, раздел «Предложение разбора»: «Если разбор нужен, он происходит в библиотеке скиллов, а не здесь». «Чужой» здесь значит «не собственный журнал библиотеки», и память проекта ждёт ровно этого: «Провести первый разбор по чужому `SIGNALS.md` — не по своему» (Фаза 8, шаг 3). Философия, раздел «Две зоны», перечисляет, что держит зона разбора: «скиллы, написанные другими людьми, недоделанные черновики, принципы, вынутые из файла, которому не принадлежали» — журнала среди этого нет; отсюда строка про `to_review/`.
- **Почему в списке сессии почти нет скиллов о скиллах.** Библиотеку читает и судит агент: весь репозиторий, `skill-anatomy`, `agent-readable`, `confidence-check`, `JUDGEMENT.md` — в его списке чтения. Сессии остаётся процедура вокруг агента: принести, вызвать, довести с владельцем, внести, записать отказ, закоммитить. Потому `skill-anatomy` в «Не грузить» — два судьи одной правки навязали бы одной задаче два набора правил, а от этого строка «Не грузить» и бережёт; `agent-readable` — только на стадии внесения, где сессия сама правит служебный файл.
- **`confidence-check` обязательным — спорная строка.** Единственное, чем этот разбор отличается от разбора своего журнала: контекст донора отсюда не проверить, а говорить о нём владельцу придётся. Описание скилла называет даты и «когда на утверждении собираются что-то строить» — разбор строит изменения на утверждениях. Собственные записи библиотеки S24, S30–S32 (по заголовкам: числа в отчёте не сходятся, числа не пересчитывались по файлу, рекомендация падала на непроверенных фактах) — про ту же слабость сессий этого репозитория.
- **Партия.** Агент в REVIEW читает весь репозиторий и увидит собственный `SIGNALS.md` библиотеки; чтобы «Анализ сигналов» не разъехался на два журнала, партию в вызове назвать словами. Форма по README агента: «Проведи REVIEW: сигналы в `<путь>` проекта <имя>, режим `сигналы`; партия — только этот файл, собственный `SIGNALS.md` библиотеки в партию не входит; памяти проекта-донора нет». Свой журнал при этом остаётся открытым на запись: библиотека — «такой же проект, как любой другой» (философия, раздел «Сигналы»), и поправки владельца по ходу разбора — сигналы для него.
- **От донора нужен только журнал.** Запись самодостаточна по устройству — абзац «что случилось» и дословная цитата, потому что «разбор не был в той сессии и увидит ровно то, что записано» (README агента). Память донора не грузится, даже если её принесли: сигнал, непонятный без неё, — находка о формате записи `signal-capture`, а не повод тянуть контекст донора.
- **Если журнал не в формате скилла.** Донор мог писать под стартовым промптом из памяти («веди `SIGNALS.md` в корне этого проекта… Цитируй меня точно») без установленного скилла — тогда записи без номеров и видов. Агент называет записи «номерами, которые они несут»; сначала привести файл к форме из раздела «Запись» `signal-capture`. Списка это не меняет, только порядок: формат — до вызова.
- **Фаза.** По заголовкам памяти идёт Фаза 5, Фазы 6–8 — план; этот разбор — шаг 3 Фазы 8, впереди шагов 1 (доноры, порог, частота разборов) и 2 (установка скилла в донор). Списка это не меняет; решения шага 1, когда появятся, лягут в тот же раздел «Фаза 8», который уже в рецепте.
- **Внесение.** Правка в три копируемых скилла или философию разводит папку агента с источником — отсюда `MANIFEST.md` и `sync_bundles.py` (знаю по манифесту). `build_catalogue.py --check` ловит устаревший каталог при правке `description` (по его докстрингу); `check_links.py` и `check_pairs.py` знаю только по именам — не читал.
